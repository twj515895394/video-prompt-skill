# Action Combat Video Prompt Spec

> 状态：设计中（Grill Me 持续收敛）
>
> 适用仓库：`video-prompt-skill`
>
> 定位：作为现有 Video Prompt Skill 的一级专项任务能力，而不是独立 Skill。

## 1. 目标

为现有 `video-prompt-skill` 增加一套动作打斗视频专项 Prompt 能力，重点解决 AI 视频中最难稳定的几类问题：

- 动作之间缺乏因果和连续性；
- 攻防关系不清楚；
- 动作与镜头彼此抢夺表达空间；
- Beat 之间切镜导致跳轴、瞬移或方向错乱；
- 打击缺少重量、接触和受力反馈；
- 复杂动作过载导致漏招、错序或肢体崩坏；
- 多人战斗时主交战关系失焦；
- 环境只是背景，没有参与动作与镜头衔接；
- 武侠动作容易在“真实武术”和“仙侠漂浮”之间失去边界。

核心目标不是建立“招式百科”，而是建立一套可复用的：

> **战斗节拍（Beat） + 动作编排（Action Choreography） + 镜头编排（Camera Choreography） + 空间连续性 + 打击反馈 + 风格强度控制**

## 2. 第一版范围

第一版并行支持两条正式分支：

1. **现代写实 / 电影化近身格斗**
2. **电影武侠 / 武术动作**

暂不把枪战纳入第一版正式实现；枪战可在共享 Combat Core 稳定后作为后续专项 Playbook 扩展。

## 3. 集成方式

确认采用：**集成进现有 `video-prompt-skill`，作为一级专项任务能力。**

不建立独立 Skill 仓库，不复制现有：

- 输入理解；
- 图生视频 / 文生视频 / 多模态处理；
- Generic / Seedance 2.0 / LTX-2.3 模型适配；
- Quick / Interactive 模式；
- 通用连续性、时间轴、风格、输出模板和诊断基础设施。

建议的任务目录：

```text
references/tasks/action-combat-video/
├── index.md
├── core-playbook.md
├── modern-combat-playbook.md
└── cinematic-wuxia-playbook.md
```

其中：

- `index.md`：识别打斗类型并路由；
- `core-playbook.md`：共享战斗结构与通用约束；
- `modern-combat-playbook.md`：现代格斗专项；
- `cinematic-wuxia-playbook.md`：电影武侠专项。

Quick Mode 下只加载：

> `Combat Core + 当前一个专项 Playbook`

不默认同时加载两个专项分支。

## 4. Combat Core 的核心组织单位：Battle Beat

确认不以“招式清单”为核心组织方式，而以 **战斗节拍 Battle Beat** 为核心。

推荐的通用 Beat 骨架：

```text
起势 / 观察
→ 首次接触 / 试探
→ 攻防交换
→ 爆发 / 战术转折
→ 缠斗 / 拉开 / 再组织
→ 终结 / 制服 / 收势
```

具体任务不要求机械包含全部阶段，应根据时长、角色数量、场景和战斗目标裁剪。

每个 Beat 至少维护以下状态：

- 战斗目标；
- 当前主攻防关系；
- 主动作链；
- 镜头目标；
- 镜头路径；
- 景别 / 角度变化；
- 双方空间与站位变化；
- 打击 / 接触 / 受力反馈；
- 节奏速度；
- 主要环境交互；
- Beat 结束状态；
- 下一 Beat 的衔接条件。

## 5. 核心原则：动作编排与镜头编排同步设计

确认采用：

> **Action Choreography 与 Camera Choreography 必须在同一个 Beat 内同步设计。**

不采用“先写完整动作，再给动作套镜头术语”的后置配镜方式。

一个 Beat 应同时回答：

1. 这一段战斗要完成什么攻防目标；
2. 主体如何行动；
3. 对手如何反应和转换攻守；
4. 镜头为什么这样拍；
5. 镜头位于双方什么关系位置；
6. 镜头沿什么路径运动；
7. Beat 结束时人物、镜头和空间停在哪里。

## 6. 时间控制：Beat 优先，时间柔性约束

确认不采用强制机械秒表式切块作为默认策略。

原则：

> **Beat 决定动作逻辑，时间负责约束整体节奏。**

允许：

- 为 Beat 分配大致时间区间；
- 对关键爆点、速度变化、对白或重要转折设置明确时间锚点；
- 根据总时长自动压缩或拆分 Beat。

避免：

- 为了填满固定秒数强塞动作；
- 每 2～3 秒机械切换一次动作；
- 秒数反过来破坏自然攻防因果。

## 7. 镜头设计：功能驱动，不以术语堆砌为目标

确认 Combat Camera 使用功能驱动链路：

> **镜头目的 → 主体关系 → 机位 → 镜头路径 → 景别变化 → 停止点**

先定义镜头要完成什么，再选择跟拍、横移、低机位、正反打、过物、环绕、拉远等手段。

示例映射：

- 看清双方站位 → 中广景 / 建立空间关系；
- 表现连续压迫 → 侧前方贴身后退跟拍；
- 放大关键重击 → 更聚焦的观察角度 + 必要的速度变化；
- 表现缠斗压迫 → 近距离横移 / 前景遮挡；
- 重新建立全局空间 → 拉开或回到建立镜头。

原则：

> **镜头服务动作，不与动作争夺复杂度预算。**

## 8. Beat 与 Shot 解耦

确认：**Battle Beat 和 Camera Shot 不强制 1:1。**

允许：

- 一个 Beat 在一个连续镜头中完成；
- 一个 Beat 包含两个短镜头；
- 相邻两个 Beat 共享同一个连续镜头。

是否切镜由功能决定，而不是由 Beat 数量决定。

常见切镜理由：

- 需要重新建立空间关系；
- 出现关键爆点；
- 攻守关系显著反转；
- 需要突出关键受力；
- 场景位置发生明显变化；
- 当前连续镜头已经无法清楚表达动作。

## 9. 跨 Beat 镜头衔接：连续运动优先

确认采用：

> **连续性优先于镜头数量；必要时才切镜。**

相邻 Beat 优先继承：

- 屏幕运动方向；
- 人物朝向；
- 镜头轴线；
- 环境锚点；
- 上一 Beat 的结束姿态；
- 尚未完全结束的动作趋势。

每次切镜必须存在明确的 **Visual Handoff（视觉接力点）**。

视觉接力可以来自：

- 攻击动作方向；
- 被击者身体运动；
- 兵器运动轨迹；
- 人物腾跃 / 转身方向；
- 衣摆、发丝等连续运动；
- 墙、柱、门框等前景遮挡；
- 主体进入 / 离开画面的方向。

## 10. 打击反馈链：关键节点强制完整

确认关键打击节点统一采用：

> **Preparation → Delivery → Contact → Reaction → Recovery → Continuation**
>
> **预备 → 发力 → 接触 → 受力反馈 → 收招 → 衔接**

关键攻击不应只描述“命中”。

应尽量明确：

- 发力前身体状态；
- 动作路径；
- 接触位置；
- 被击者受力和失衡；
- 攻击者自身的收招和重心恢复；
- 必要的环境反馈；
- 下一动作如何自然承接。

现代格斗与电影武侠共享这一因果链，但表现不同：

### 现代格斗

强调：

- 重量；
- 惯性；
- 失衡；
- 短促反馈；
- 恢复时间；
- 真实接触感。

### 电影武侠

强调：

- 借力；
- 身法；
- 兵器轨迹；
- 衣摆 / 身体线条；
- 更优雅的攻防转换；
- 仍然明确的起力、受力与落位。

## 11. 动作复杂度预算

确认每个 Beat 默认限制为：

> **1 个主攻防目标 + 2～4 个连续微动作 + 1 个明确结束状态**

当用户输入大量招式时，Skill 应优先：

1. 找出当前 Beat 的主攻防目标；
2. 保留最有价值的 2～4 个微动作；
3. 将关键爆点单独保留；
4. 把多余动作拆到后续 Beat；
5. 删除不影响主线的动作噪音。

核心原则：

> **动作丰富度服从可读性；宁可少而清晰，也不要多而混乱。**

## 12. 1v1 与 1vN

确认第一版正式支持：

- `1v1`
- `1vN`

多人战必须采用：**主交战对象机制**。

规则：

- 每个 Beat 只有一个主交战关系；
- 镜头只服务当前主交战关系；
- 其他对手必须处于明确状态；
- 切换主对手时必须重新建立空间和视觉接力。

非主交战对象可处于：

- 逼近；
- 包抄；
- 被阻挡；
- 刚被击退；
- 倒地恢复；
- 等待切入；
- 被环境隔开。

禁止默认生成“多人同时无序挥打”的混战结构。

## 13. 环境作为一级战斗变量

确认环境不是单纯背景，而可以主动参与：

> **移动 → 遮挡 → 借力 → 碰撞 → 改变站位 → 镜头接力**

现代格斗可利用：

- 墙面；
- 门框；
- 柱体；
- 桌椅；
- 楼梯；
- 栏杆；
- 狭窄走廊；
- 车辆或其他场景障碍。

电影武侠可利用：

- 竹林；
- 石阶；
- 屋顶；
- 廊柱；
- 桌案；
- 门窗；
- 树干；
- 栏杆；
- 高低地形。

复杂度限制：

> **每个 Beat 最多突出 1 个主要环境交互。**

## 14. 速度变化与慢动作

确认 Skill 可以自动设计有限速度变化，但必须功能驱动。

规则：

- 正常速度承担主要攻防与空间推进；
- 关键重击、兵器交错、极限闪避、腾跃转折等可短暂减速；
- 一个 Beat 原则上最多 1 个速度变化重点；
- 减速之后尽快恢复正常速度；
- 必须明确“慢下来是为了看清什么”。

禁止仅为了“电影感”长期慢动作。

现代格斗更偏：

- 短促爆点；
- 接触瞬间；
- 受力瞬间。

电影武侠可适度用于：

- 兵器交错；
- 身法转换；
- 腾跃转折；
- 落位前后的动作线条。

## 15. 现代格斗强度等级

确认现代格斗采用三级强度体系：

### Level 1｜写实近身格斗

- 强调真实防守；
- 真实重心；
- 短动作；
- 明确受力与恢复；
- 接近现实攻防节奏。

### Level 2｜电影化现代动作（默认）

- 保持写实物理基础；
- 更利落的连击；
- 更强的攻防转换；
- 更清楚的动作展示；
- 更积极的镜头配合。

### Level 3｜强化动作片

- 更高密度攻防；
- 更强环境利用；
- 更明显的爆点；
- 仍禁止超级英雄式无重量感战斗。

## 16. 电影武侠身法等级

确认电影武侠采用三级身法强度：

### Level 1｜写实武术

- 基本不超出现实人体合理范围；
- 强调真实重心、步法、翻滚、借力和落地。

### Level 2｜电影武侠（默认）

允许：

- 短距离腾跃；
- 踏墙；
- 滑步；
- 借力飞身；
- 轻微滞空。

但必须保留：

- 明确起跳；
- 明确受力来源；
- 明确运动路径；
- 明确落地；
- 明确空间关系。

### Level 3｜高武武侠

允许：

- 更长距离飞跃；
- 更明显滞空；
- 更强化的身法夸张。

仍然不进入：

- 剑气；
- 能量波；
- 御剑飞行；
- 法器；
- 长距离无支撑飞行；
- 其他仙侠 / 超自然能量体系。

## 17. 电影武侠兵器范围

确认第一版正式支持常见四类：

- 刀；
- 剑；
- 枪；
- 棍。

不追求十八般兵器全覆盖。

兵器 Beat 重点控制：

- 握持与身体关系；
- 合理攻防距离；
- 兵器运动轨迹；
- 格挡 / 招架；
- 借力 / 偏转；
- 兵器接触反馈；
- 身体重心变化；
- 兵器轨迹与镜头协同；
- 攻防后的落位。

## 18. 流派动作画像

确认支持格斗 / 武术“流派动作画像”，但不建设招式百科。

每个流派重点定义：

- 典型交战距离；
- 重心和站姿；
- 发力方式；
- 攻防节奏；
- 常见动作类型；
- 身体姿态；
- 连续攻击倾向；
- 防守习惯；
- 空间移动方式；
- 镜头应该重点表现什么。

现代格斗候选画像可包括：

- Boxing；
- Muay Thai；
- Sanda；
- MMA；
- 摔跤 / 柔术倾向；
- 电影化战术近身动作语言。

武术 / 武侠候选画像可包括：

- 咏春；
- 八极；
- 太极式借力；
- 长拳；
- 南拳；
- 刀法；
- 剑法；
- 枪法；
- 棍法。

流派名称不是 Prompt 装饰标签，而必须实际改变动作距离、重心、节奏和镜头重点。

## 19. 混合流派

确认支持：

> **主流派 + 辅助流派**

例如：

- 拳击主导 + 摔跤辅助；
- 泰拳主导 + MMA 控制辅助；
- 咏春主导 + 八极爆发辅助；
- 剑法主导 + 轻身步法辅助。

限制：

> **一个 Beat 只能有一个主动作语言。**

辅助流派只能在明确的攻防转换节点介入，禁止把多个体系同时堆入同一个 Beat。

预计需要新增 / 扩展以下能力，但最终路径仍需在实施阶段审计现有真源后确定。

### Tasks

├── index.md

### Controls（候选）

- `continuity-consistency`

进行职责审计，避免重复真源。

### Libraries（候选）

可能采用一个 Combat Library 加内部章节，也可能拆为现代 / 武侠子库；此项尚未最终确认。

候选内容包括：

- 现代格斗动作画像；
- 武术 / 武侠动作画像；
- 兵器动作画像；
- 打斗镜头功能映射；
- 战斗环境交互模式。

### Styles（候选）

- 现代电影动作；
- 电影武侠。

是否新增独立 style 文件，还是扩展现有 cinematic / genre 真源，尚待职责审计。

### Diagnostics（候选）

未来可能针对：

- 打斗动作混乱；
- 攻防空间错乱；
- 打击反馈过弱；
- 武侠动作漂浮 / 无因果；
- 多人战目标失焦。

正式新增前优先检查现有：

- `motion-discontinuity`
- `camera-chaos`
- `spatial-teleportation`
- `anatomy-contact-failure`
- `physics-and-weightlessness`
- `prompt-overload-and-conflict`

是否已经能够承担主诊断职责。

## 21. Quick / Interactive 模式

Combat 能力不改变现有模式原则。

### Quick Mode

默认：

- 不追问；
- 自动选择合理 Combat 类型和强度；
- 自动拆 Beat；
- 自动控制动作复杂度；
- 自动设计动作与镜头协同；
- 直接交付可复制 Prompt。

若用户没有指定：

- 现代格斗默认 Level 2；
- 电影武侠默认 Level 2；
- 默认以可读性优先，而不是动作数量优先。

### Interactive Mode

只有用户明确要求讨论 / Grill Me 时启用。

继续遵守：

- 一次只问一个关键问题；
- 每个问题提供推荐答案；
- 按设计依赖顺序推进；
- 已确认项不重复追问。

## 22. 当前明确禁止的设计倾向

- 不把打斗设计成动作名词堆砌；
- 不默认一个 Beat 塞大量招式；
- 不让镜头与主体动作同时高复杂度运动；
- 不无理由频繁切镜；
- 不允许切镜后人物站位和运动方向无接力；
- 不把“命中”当作完整打击反馈；
- 不让多人同时无序成为主交战对象；
- 不让环境同时承担过多交互；
- 不滥用慢动作；
- 不让流派名只成为装饰标签；
- 不默认将电影武侠扩展为仙侠；
- 不把真实武术和高武身法混在同一强度级别；
- 不复制现有 v2 controls / diagnostics 已经拥有的通用真源。

## 25. 当前设计结论

当前 Combat 模块的基本哲学可以压缩为：

> **先建立可读的战斗 Beat，再同步设计动作与镜头；让空间、受力、环境和速度变化共同服务攻防因果；复杂度必须服从连续性与可执行性。**
